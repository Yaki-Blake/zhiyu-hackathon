## 会话、事件与反馈（11/20，B2-3）

PDF 对 B2-3 的三条验收是：双击提交只存一份、伪造版本返回 409、访问/点击/自报完成三列分别正确。前两项原有实现已经满足，第三项的口径只写在文档里、没有测试守着。本轮把它变成可执行断言，并顺带发现一处数据缺陷。

| 改动 | 原因 | 验证 |
| --- | --- | --- |
| 同一会话换 `submissionId` 再提交改返回 409 | 原实现靠 `INSERT OR IGNORE` 忽略冲突，随后把旧回执以 200 返回。读者改口报「已完成」，接口说成功，看板仍是「卡住」，三列计数直接失真 | `test_different_submission_id_from_same_reader_is_rejected` |
| `submissionId` 跨会话撞号改为 409 | 唯一索引是 `(slug, sid)`，两个读者用同一 id 时后者的插入被静默忽略，原实现会返回空回执 + 200 | `test_two_readers_each_keep_their_own_row` |
| 新增 17 组事件用例 `test_events.py` | 原 `test_flow` 只走一遍主干，并发双击、被拒事件是否留痕、版本隔离、撤回后的行为都没有覆盖 | 全绿 |
| 新增 `runs` 留存清理 | `runs` 每次匹配写一条、带完整候选与快照，是唯一会自己长大的表；无上限会在长跑中拖慢备份 | `test_deploy.Retention` 5 组 |

`test_events.py` 覆盖的边界，按验收条款归位：

- 三列口径：只访问、访问后打开、打开后完成，三步分别断言 `(1,0,0)`、`(1,1,0)`、`(1,1,1)`；重复访问与重复打开不累加；只打开不访问也算一次访问；报「卡住」不计入完成。
- 双击：同一 `submissionId` 连发两次与并发两次都只落一行且回执相同；不同 `submissionId` 并发时严格一个 200、一个 409。
- 伪造版本：`version` 不符时 `visit`、`open`、`feedback` 全返回 409，且事后 `visits`、`feedback` 两表都是 0 行（事务回滚没有留下半个事件）。
- 作用域：新旧版本各自计数；撤回后新事件 404 但历史计数保留；未知 slug 返回 404 而非 400。
- 负载：12 个读者 24 次写并发，计数精确为 `(12,12,0)`；6 个读者并发反馈后 `visits ≥ completed`。

留存策略（`server.prune` + `scripts/prune.py`）：默认保留 90 天；被 `cards.run_id` 引用的运行永不删除，否则反馈追不回当时展示的候选；`visits`、`feedback` 一行不动，删了等于改写历史统计。脚本默认只报告不删除，加 `--apply` 才执行。

## 真机验证（11/20，USB 直连手机）

设备：小米 2602BRT18C，1280×2772 / 520dpi（CSS 视口约 394dp），MIUI，Android 17，浏览器为系统内置浏览器。

做法：手机与电脑在同一可互访网段（手机 10.114.96.143 → 电脑 172.31.26.77，ping 12.9 ms），本机实例用 `--host 0.0.0.0` 对外监听，`ZHIYU_HOSTS` 加上电脑 IP。

结论：首页（开发者工作台）在真机上渲染完全正常——导航四列、面包屑、示例卡片、按钮都无溢出，与桌面模拟的结论一致。**但真机试出了桌面模拟查不出的一个阻塞级缺陷。**

### 阻塞级缺陷：明文访问下读者端直接报错

点「试跑访谈稿示例」时页面顶部弹出红色错误条 `crypto.randomUUID is not a function`，页面停在原地不跳转，读者无法提交反馈。

根因：`crypto.randomUUID()` 按规范**只在 secure context（HTTPS 或 localhost）暴露**。手机走 `http://172.31.26.77:4199` 这种明文非回环地址，不算安全上下文，该方法为 `undefined`，调用即抛 TypeError。

影响两处，都在 F1 的 `app.js` 里：

| 位置 | 用途 | 症状 |
| --- | --- | --- |
| `app.js:117` | 场景匹配的 `requestId` | 开发者在手机上跑不了匹配 |
| `app.js:151` | 读者反馈的 `submissionId` | 读者提交不了反馈 |

要点：浏览器证书无效的 HTTPS **同样不算** secure context，自签证书救不了这条路。

结论与处置：

- 正式部署走域名 + HTTPS 就没有这个问题（本来也必须走 HTTPS），所以不是上线阻塞。
- `docs/DEPLOY.md` 第 1 节的路线 C（`http://IP:4173`，无备案时的兜底）会直接踩中，**已加前端兜底修复，见下方「修复」小节**。

### 顺带改的服务端

`server.py` 新增 `--host` 参数（等价环境变量 `ZHIYU_HOST`，默认 `127.0.0.1`，默认行为不变），让本机实例能对同网段设备开放。`ZHIYU_HOSTS` 白名单仍然生效：实测 `Host: evil.example` 返回 403，白名单内的 IP 直连返回 200。

证据截图在本机 `var/phone/`（已 gitignore，不入库）。

### 对照核验与全链路走通（11/20 12:27-12:37，第二轮真机）

用户重新接入手机后复验，代码未变（`app.js` 两处 `randomUUID` 都还在）：

1. **缺陷原样复现**：手机走 `http://172.31.26.77:4199` 点示例按钮，仍报 `crypto.randomUUID is not a function`。
2. **对照坐实根因**：同一台手机、同一份代码，改用 `adb reverse` + `http://localhost:4199` 访问（localhost 属 secure context），点同一按钮**正常跳到匹配页，无错误**。`crypto.randomUUID` 在这里能生成标准 UUID（库里落库的 `sid` 形如 `c408ed61-d63f-...`）。至此确认是**访问来源的安全上下文属性**问题，不是代码逻辑坏了。
3. **在 secure context 下把全链路走通**（此前因崩溃从未跑到这里）：匹配场景 → 编辑试用卡 → 预览 → 确认发布（读者链接与版本记录正常）→ 打开读者卡（步骤编号无重号，上轮的种子数据修复生效）→ 选「做完了」填反馈 → 提交（提示「反馈已收到·做完了／已归入 v1。刷新页面也不会重复提交。」）→ 读者反馈看板四项统计 **访问 1 / 进入工具 0 / 自报完成 1 / 具体反馈 1**，与数据库 `visits`/`feedback` 实际行数完全一致。
4. 全流程在 394dp CSS 视口下无横向溢出、无文字截断、按钮可点，软键盘弹起时布局不破。

结论：只要走 HTTPS 或 localhost，B2 交付的数据链在真机上完整可用；明文 IP 的问题经用户授权后已修复，见下。

证据截图 `var/phone/v2-01..v2-21.png`（21 张，已 gitignore）。

### 修复（11/20 12:50，用户选 A 授权）

在 `app.js` 顶部注入兜底：原生 `crypto.randomUUID` 缺失时，用任何上下文都可用的 `crypto.getRandomValues` 补一个 v4 格式的 UUID。只补缺失的方法，不改既有逻辑。

三处关键约束，都写进 `test_frontend_contract.py`（4 组）守着：

1. **补丁只能在 `app.js`，不能内联到 `index.html`** — CSP 是 `script-src 'self'` 且无 nonce，内联脚本会被静默拦掉。
2. **不能给 `globalThis.crypto` 重新赋值** — `window.crypto` 是只读访问器，严格模式下赋值抛 TypeError，整段脚本停摆（页面卡在「正在打开知遇…」）。第一版补丁就踩了这个坑，已修正为只往现有对象上加方法。
3. **两处调用点必须在兜底之后** — `app.js:117`（requestId）与 `:151`（读者 sid）。

验证：Node 生成 1000 个 UUID 全部格式合法且唯一；桌面 Chrome 走同样的明文 IP `http://172.31.26.77:4199`，`typeof crypto.randomUUID === "function"`，点示例按钮成功跳到 `#match/...`，无错误条；反向验证——把兜底条件改成 `if(false)` 后契约测试确实报 FAILED。全量回归 57 组测试 + 30 项黑盒通过。

一个运维坑：静态资源 `Cache-Control: max-age=300`，真机验证时浏览器缓存了旧的坏 `app.js`，改完文件手机仍是旧版，清缓存后才生效。演示前若改过前端资源，记得强刷或加版本查询串。

证据截图 `var/phone/fix-*.png`。

## 与规划书的偏差（以此为准）

1. 读限流改为进程内存计数，不落 `limits` 表，重启清零。写限流仍落库。
2. 新增进程内 `WRITE_LOCK`：SQLite 单写者，并发写会偶发 `readonly database`，串行后消失。5 并发 p95 约 100 ms。
3. 会话值校验从 32 字符放宽到 16 至 64 字符：演示工作区的 owner 由 `uid()` 生成，长度 24。
4. 索引改在补列之后创建，否则旧库启动即失败。
5. 恢复码可重复使用，直到轮换；不是一次性凭据。
6. 备份脚本依赖 `sqlite3` 命令行，服务器需安装。
7. 写限流计数独立成一个事务，先提交再处理业务；代价是每个写请求多一次 `BEGIN IMMEDIATE`，5 并发 p95 从约 60 ms 升到约 100 ms。
8. `runs` 增设 90 天留存，被已发布卡片引用的行永久保留。规划书没有定义清理策略，这是本轮补的运维约定，实现在 `server.prune` 与 `scripts/prune.py`。
